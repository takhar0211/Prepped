INTERVIEW PREPARATION GUIDE - DSA PREP HUB
================================================================================

1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
Project Name: DSA Prep Hub (AI Interview Platform)

What problem it solves: 
Traditional coding platforms (like LeetCode) only verify if a candidate's code passes test cases. However, real technical interviews require candidates to explain their thought process, analyze time and space complexity, discuss edge cases, and optimize their code. This project bridges the gap by simulating a real interview environment where an AI interviewer follows up on the candidate's code.

Why it was built: 
To provide a complete, realistic, end-to-end technical interview simulation that goes beyond just writing code, helping candidates build communication and analytical skills.

Target users: 
Software engineering candidates preparing for technical interviews (FAANG or general tech companies).

Main features:
- Integrated Code Editor (Monaco Editor) for Python, C++, Java, JS, and SQL.
- Secure, fast local code execution engine using native compilers/interpreters.
- Conversational AI Interviewer (Alex) that grills the candidate on their submitted code.
- Voice-to-Text integration using Sarvam AI for natural spoken responses.
- On-demand Mock Interview generation tailored to specific topics and difficulty.
- AI-generated comprehensive performance report and scorecard.

End-to-end workflow:
1. User logs in to the dashboard.
2. User configures a custom Mock Interview (e.g., "Medium DSA questions on Trees") or picks a recommended question.
3. User enters the interview room and sees the problem description and starter code.
4. User writes code and clicks "Run" to test against example cases (sandbox execution).
5. User clicks "Submit". If all test cases pass, the coding phase ends.
6. The AI Interviewer phase begins instantly. "Alex" asks follow-up questions about time/space complexity and optimizations.
7. User responds via text or microphone (Speech-to-Text).
8. Once the mock interview is finished, the system generates a detailed scorecard highlighting strengths and weaknesses.


2. PROJECT ARCHITECTURE
--------------------------------------------------------------------------------
Overall Architecture:
The project follows a standard Client-Server architecture. The frontend is a Single Page Application (built with Next.js/React) that communicates via RESTful APIs with the backend (built with Django). The backend interacts with a relational database (SQLite), a local code execution sandbox (using Python's subprocess module), and external AI APIs (Google Gemini, Sarvam AI).

Frontend -> Backend -> Database Flow:
1. The Next.js frontend sends an HTTP POST request with the user's code to the Django backend.
2. The Django View receives the code, validates the session, and triggers the `validate_code` utility.
3. The utility writes the code to a temporary file, runs it using a native OS process, and captures standard output/error.
4. Results are checked against the Database's expected outputs for the question's test cases.
5. A submission record is saved to the SQLite database.
6. The backend returns the execution results to the frontend in a JSON response.

Request/Response Lifecycle:
Client -> HTTP Request -> Django Middleware (Auth/CORS) -> Django URL Router -> Django View -> Business Logic (Subprocess / LLM) -> Database Query -> JSON Serialization -> HTTP Response -> Client UI Update.

Authentication Flow:
The app uses Django Session Authentication. When a user logs in, Django validates the credentials against the SQLite database, creates a session ID, and sets a secure HTTP-only cookie in the user's browser. Subsequent requests from the frontend automatically include this cookie to prove the user is authenticated.

High-Level ASCII Diagram:

   [ Next.js Frontend ]
      |        ^
   (HTTP)   (JSON)
      v        |
   [ Django REST API (Backend) ]  <---> [ Local Code Execution Sandbox ]
      |        ^                          (Subprocess: Python, g++, javac, node)
  (ORM)     (Data)
      v        |
   [ SQLite Database ]
      
      |
   (API Calls over HTTPS)
      v
   [ External AI APIs (Gemini LLM, Sarvam Speech-to-Text) ]


3. TECH STACK
--------------------------------------------------------------------------------
Frontend:
- Next.js / React: A React framework for building user interfaces. Used because it provides built-in routing, fast performance, and an easy mental model for component-based UI. Chosen over raw React for better file-based routing.
- TailwindCSS: A utility-first CSS framework. Used for rapid UI styling without writing separate CSS files.
- Monaco Editor: The code editor that powers VS Code. Used to provide a professional coding experience with syntax highlighting and indentation.

Backend:
- Django / Django REST Framework (DRF): A high-level Python web framework. Used to quickly build secure and scalable REST APIs. Chosen over FastAPI/Flask because of its built-in ORM, admin panel, and robust authentication system.
- Python Subprocess: A native Python module used to spawn new processes. Used to safely execute user-submitted code in isolation instead of relying on a slow, error-prone LLM to evaluate code correctness.

Database:
- SQLite: A lightweight, file-based relational database. Used to store users, questions, submissions, and interview sessions. Chosen because it requires zero configuration and is perfect for prototyping and hackathons.

AI / LLMs:
- Google Gemini (gemini-2.5-flash): A fast Large Language Model accessed via Langchain. Used to generate dynamic interview questions, conduct conversational follow-ups, and generate final scorecards. Chosen over GPT-4 for speed and cost-effectiveness.
- Sarvam AI: A specialized API for speech-to-text processing. Used to allow users to speak their answers.


4. FRONTEND
--------------------------------------------------------------------------------
Folder Structure:
- /app: Contains Next.js routes and pages.
- /app/interview/[id]/page.tsx: The main interview room component.
- /lib/api.ts: Axios instances and API endpoint definitions.
- /public: Static assets (icons, SVGs).

Important Files:
- app/interview/[id]/page.tsx: The core file of the frontend. It manages multiple states: coding phase, test case results, timer, and the AI chat interface. It utilizes `useRef` for the timer and chat auto-scrolling, and `useState` for code, language, and run status. 
- lib/api.ts: Centralizes all API calls (axios) so components don't have to hardcode URLs.

Routing:
Uses Next.js App Router (file-system based). Navigating to `/interview/123` dynamically loads the interview room for question ID 123.

State Management:
Uses local React state (`useState`, `useEffect`) rather than Redux. This keeps the application lightweight. State includes `timeLeft`, `code`, `chatHistory`, and `runStatus`.

API Calling:
Uses Axios to make asynchronous HTTP requests to the Django backend. The responses update the local state.


5. BACKEND
--------------------------------------------------------------------------------
Folder Structure:
- /server/api: The main Django app containing models, views, and utilities.
- /server/backend: The Django project configuration folder (settings.py, urls.py).

Important Files:
- models.py: Defines the database schema using Django ORM.
- views.py: Contains the API endpoints (e.g., `RunCodeView`, `SubmitCodeView`, `GenerateInterviewView`). Maps HTTP requests to business logic.
- utils.py: Contains the core logic. Has functions for communicating with Gemini (`generate_interview_questions`, `interview_follow_up`) and the `validate_code` function which runs user code natively.
- runner.py: Generates wrapper code (test harnesses) for different languages to securely run and test user code.

Request Flow:
1. Client calls `/api/submit-code/`.
2. `SubmitCodeView` fetches the `Question` from the DB.
3. View calls `validate_code` in `utils.py`.
4. `validate_code` calls `generate_python_wrapper` in `runner.py`, saves to a temp file, and runs it via `subprocess.run`.
5. Outputs are captured, evaluated, and returned to the View.
6. If the code passed, the View creates an `InterviewSession` in the DB and triggers `interview_follow_up` (LLM).
7. View returns JSON to the Client.


6. DATABASE (Highest Priority)
--------------------------------------------------------------------------------
Which database is used: 
SQLite.

Why this database was chosen:
SQLite is built directly into Python. It requires no separate server process, making it extremely easy to set up, deploy, and develop with during a rapid prototyping phase or hackathon.

Why not MySQL/PostgreSQL/MongoDB:
- vs PostgreSQL/MySQL: Setting up a full Postgres server requires Docker or a remote managed database, which adds deployment overhead. For a project with low initial traffic, SQLite is sufficient. (Note: For a real production launch with thousands of concurrent users, PostgreSQL would be strictly necessary to handle concurrent writes).
- vs MongoDB: This project has highly structured, relational data (Users -> Submissions -> Questions). A relational database (SQL) is much better suited for enforcing these relationships via Foreign Keys than a NoSQL document store like MongoDB.

Tables and Relationships:
1. UserProfile:
   - Extends the built-in Django `User` model (One-to-One relationship).
   - Stores `leetcode_username` and `streak_count`.

2. Question:
   - Stores problem details: `title`, `description`, `difficulty`, `examples`, `test_cases`, `starter_code`.
   - Primary Key: `id`.

3. Submission:
   - Records every code submission.
   - Foreign Keys: `user_id` (Many-to-One to User), `question_id` (Many-to-One to Question).
   - Stores `code`, `language`, `status` (Accepted/Rejected).

4. MockInterview:
   - Represents a configured mock interview session.
   - Foreign Key: `user_id` (Many-to-One to User).
   - Many-to-Many Relationship: Connects to `Question` (a mock interview has multiple questions, and a question can be in multiple mock interviews).
   - Stores `topic`, `difficulty`, `time_limit`, `status`, and the final AI `performance_summary`.

5. InterviewSession:
   - Links a submission to an AI chat session.
   - Foreign Keys: `user_id`, `question_id`.
   - One-to-One: Links exactly to one `Submission`.
   - Stores the `chat_history` as a JSON field.

6. QuestionPerformance:
   - Tracks how well a user did on a specific question within a MockInterview.
   - Foreign Keys: `mock_interview_id`, `question_id`.
   - Stores `status`, `time_spent`, `attempts`, `interview_brief`.

How data flows (CRUD operations):
- Create: When a user submits code, a new `Submission` row is created.
- Read: The dashboard fetches the user's `MockInterview` history to display stats.
- Update: As the user chats with the AI, the `chat_history` JSON field in `InterviewSession` is updated and saved.
- Delete: Standard cascading deletes; if a User is deleted, their Submissions and MockInterviews are deleted automatically.

Performance Optimizations:
- Using `select_related()` or `prefetch_related()` in Django when fetching mock interviews and their associated questions to prevent N+1 query problems.
- Storing `chat_history` as a JSON field rather than creating a separate SQL table for every single message saves database joins and speeds up read/write times for the chat.

Security considerations:
- Database injection is prevented automatically by using Django's ORM, which safely escapes all SQL parameters.

Common Interview Questions related to this DB:
- Q: "Why did you use JSON fields for test cases instead of a separate TestCases table?"
- A: "Test cases are tightly coupled to a single question and are always loaded together. Since we don't need to query test cases independently, storing them as a JSON array in the Question table reduces JOINs and speeds up reads."

8. IMPORTANT CONCEPTS USED
--------------------------------------------------------------------------------
- Subprocess Sandboxing:
  What it is: Running external terminal commands from within a Python script.
  Why it is used here: To execute untrusted user code in isolation.

- Prompt Engineering:
  What it is: Designing specific instructions for Large Language Models.
  Why it is used here: To force the AI interviewer ("Alex") to ask exactly one question at a time and not reveal the answer directly.

- RESTful API Architecture:
  What it is: A standard for building web APIs using HTTP methods (GET, POST).
  Why it is used here: To create a clean separation of concerns between the Next.js frontend and Django backend.

- JSON Data Types in SQL:
  What it is: Storing unstructured or semi-structured data (like chat history) directly in a database column.
  Why it is used here: To avoid creating complex relational tables for simple lists of messages or test cases.


9. INTERVIEW PREPARATION (Roleplay Answers)
--------------------------------------------------------------------------------
Pretend you are the developer who built this:

"Tell me about your project."
My project is a technical interview simulation platform. Unlike standard coding platforms that just check if your code compiles, my platform simulates a real interview. You write code, and once it passes, an AI interviewer actively chats with you, asking you to explain your time complexity, space complexity, and how you might optimize the solution. At the end, it generates a performance scorecard.

"Why did you build it? What problem does it solve?"
I built it because I realized passing test cases on LeetCode doesn't prepare you for the communication aspect of an interview. Real interviews require you to defend your decisions and handle follow-up questions. This solves that problem by forcing candidates to explain their code to an AI before they can consider the problem "solved."

"Explain the architecture."
It's a decoupled client-server architecture. The frontend is built with Next.js and Tailwind, communicating via a REST API to a Django backend. The backend uses SQLite for data storage. For code execution, instead of using a slow LLM, I implemented a local execution sandbox using Python's subprocess module. For the conversational AI, I integrated Google's Gemini API via Langchain.

"Explain the database."
I used SQLite managed via Django's ORM. The core models are User, Question, Submission, and MockInterview. A MockInterview has a many-to-many relationship with Questions. When a user submits code, it creates a Submission tied to a Question and User. If it passes, a One-to-One InterviewSession is generated to store the chat history in a JSON field.

"Explain the tech stack. Why did you choose these technologies?"
I chose Next.js for the frontend because its file-based routing makes building multi-page apps very fast. I used Django for the backend because its built-in ORM and admin panel allowed me to model complex relational data (like mock interviews and submissions) rapidly. I chose Gemini over GPT-4 because it's significantly faster and cheaper, which is crucial for a real-time chat interface.

"What challenges did you face? (5 challenges and solutions)"
1. Challenge: Evaluating user code accurately.
   Solution: Initially, I thought about using an LLM to evaluate code, but LLMs hallucinate. I solved this by writing a custom code execution engine (`runner.py`) that uses Python's `subprocess` to compile and run the code natively against test cases.
2. Challenge: Infinite loops crashing the server.
   Solution: When running user code locally, an infinite loop would hang the backend. I solved this by passing a strict `timeout=5` argument to the `subprocess.run` command, terminating any runaway code safely.
3. Challenge: Keeping the AI interviewer on track.
   Solution: The LLM would often give away the answer immediately or ask 5 questions at once. I solved this through strict prompt engineering, passing the exact chat history and explicitly instructing the system prompt to ask only one question at a time and never reveal the code.
4. Challenge: Handling different programming languages.
   Solution: Python, Java, C++, and JS all have different entry points. I wrote dynamic wrapper scripts for each language that takes the user's function, injects it into a standard template, and prints the output with a specific delimiter so my Python backend could parse the results cleanly.
5. Challenge: Running out of database questions for custom interviews.
   Solution: If a user requested a specific topic that wasn't in my DB, the app would fail. I implemented a fallback mechanism where the backend calls the LLM to generate a brand-new question, saves it to the DB instantly, and then serves it to the user.

"What did you learn from this project?"
I learned how to integrate traditional software engineering (secure code execution, sandboxing, relational databases) with modern Generative AI. I learned that LLMs are great for conversation, but terrible for deterministic tasks like running code, which taught me to always use the right tool for the job.

"What improvements would you make in the future?"
I would migrate the database from SQLite to PostgreSQL for better concurrency. I would also move the code execution engine out of the main Django server and into isolated Docker containers using a message queue like Celery, ensuring maximum security and scalability.

"What impact does the project have?"
It dramatically lowers the barrier to getting realistic interview practice. Instead of needing to schedule a mock interview with a human peer, candidates can instantly practice their communication skills 24/7.


10. MOST IMPORTANT INTERVIEW QUESTIONS (Top 25)
--------------------------------------------------------------------------------
1. Q: How does your code execution sandbox work?
   A: The backend wraps the user's code in a template, writes it to a temporary file, and uses Python's `subprocess` module to compile and execute it with a strict 5-second timeout.

2. Q: How do you prevent malicious code (like `os.system('rm -rf /')`) from running on your server?
   A: Currently, it relies on basic timeouts, but for a production environment, I would isolate the execution inside unprivileged, ephemeral Docker containers without network access.

3. Q: Why did you choose Django over Express.js or FastAPI?
   A: Django provides a robust ORM and built-in models out of the box, which allowed me to rapidly model the complex relationships between Users, Submissions, and Mock Interviews without writing raw SQL.

4. Q: How does the AI Interviewer maintain context of the conversation?
   A: I store the entire chat history in a JSON field in the database. On every new message, I fetch the history, append the new message, and send the entire log back to the Gemini API as context.

5. Q: What is a Many-to-Many relationship, and where is it used in your project?
   A: It's when multiple records in one table relate to multiple records in another. It's used between `MockInterview` and `Question`—one mock interview contains many questions, and one question can belong to many mock interviews.

6. Q: Why store `chat_history` as JSON instead of creating a `Message` SQL table?
   A: Chat logs are always retrieved and updated sequentially as a single unit. Storing them as JSON avoids costly database JOINs and simplifies the schema.

7. Q: How do you handle language detection if a user submits Python code but selects C++?
   A: I wrote a lightweight regex-based heuristic function (`_detect_language`) in `utils.py` that checks for structural clues (like `def` for Python or `#include` for C++) and auto-corrects the language.

8. Q: How do you handle mapping compiler errors back to the user's original code?
   A: Because I inject the user's code into a wrapper, the line numbers change. I calculate the line number offset during generation and use regex to subtract that offset from the standard error output before showing it to the user.

9. Q: What happens if the Gemini API goes down or takes too long?
   A: The frontend will show a loading state. For a production app, I would implement retry logic, fallbacks to a secondary LLM provider, and proper error handling to inform the user gracefully.

10. Q: Why use React/Next.js for the frontend?
    A: React's component-based architecture allows for highly interactive UI (like the code editor side-by-side with the chat). Next.js provides App Router, making it easy to create dynamic routes like `/interview/[id]`.

11. Q: How do you prevent users from getting the same question twice in a mock interview?
    A: The backend queries the `Submission` table to find questions the user has already solved, and actively uses `.exclude(title__in=all_solved)` in the Django ORM query when picking new questions.

12. Q: What is a Foreign Key, and give an example from your project.
    A: A Foreign Key links a row in one table to a row in another. In my `Submission` table, `user_id` is a foreign key linking to the `User` table.

13. Q: How is user state managed in the frontend?
    A: I use standard React hooks (`useState` and `useEffect`) to track the current code, timer, and chat history.

14. Q: What happens if a user refreshes the page during an interview?
    A: Because the backend is stateless REST and the interview session state (chat history, submissions) is saved in the database, the user can fetch their session data on load and resume. (Note: The frontend timer might reset depending on implementation, which is an area for improvement).

15. Q: How did you design the REST API endpoints?
    A: I used noun-based routing (e.g., GET `/api/mock-interview/<id>` to fetch details) and verbs for actions (e.g., POST `/api/submit-code/` to trigger the execution logic).

16. Q: What's the difference between `Run` and `Submit` in your application?
    A: `Run` validates the code against a small set of public examples (for fast debugging). `Submit` tests the code against ALL hidden test cases and, if successful, creates a permanent database record and triggers the AI interview.

17. Q: How does the speech-to-text functionality work?
    A: The frontend uses the browser's native `MediaRecorder` or `SpeechRecognition` API. Alternatively, it sends audio files to the Sarvam AI API backend proxy, which returns the transcribed text to populate the chat input.

18. Q: Why use SQLite? Is it suitable for production?
    A: I used it for rapid development. It is NOT suitable for high-concurrency production environments because it uses database-level locking during writes, which bottlenecks traffic.

19. Q: How would you scale this application?
    A: Move the database to PostgreSQL. Implement Redis for caching LLM responses and rate-limiting. Offload the `subprocess` code execution to a scalable Kubernetes cluster of isolated workers using Celery.

20. Q: Describe the prompt engineering techniques you used.
    A: I used "System Prompts" to define Alex's persona, provided strict structural constraints (e.g., "Ask ONE question at a time"), and passed the candidate's code and chat history as explicit context blocks.

21. Q: How does your frontend communicate with the backend securely?
    A: It uses HTTP requests with Session/Basic Authentication. CORS (Cross-Origin Resource Sharing) is configured in Django to only accept requests from the frontend domain.

22. Q: What is the N+1 query problem, and did you face it?
    A: It occurs when an ORM executes 1 query to get a list, and then N additional queries to get related data for each item. I optimized this using Django's `select_related` and `prefetch_related`.

23. Q: How did you implement the fallback for when the DB doesn't have enough questions?
    A: The view queries the DB. If `len(questions) < requested_amount`, it calls an LLM function that generates structured JSON questions, saves them immediately to the DB via `get_or_create`, and appends them to the interview.

24. Q: How does the AI generate the final performance report?
    A: Once the interview concludes, a separate API endpoint gathers all `QuestionPerformance` data for that mock interview and sends it to Gemini with a strict JSON schema prompt to output scores and feedback.

25. Q: If you had 2 more weeks to work on this, what would you add?
    A: I would add real-time collaborative coding (like WebSockets for a human-to-human mode), proper Docker containerization for the sandbox, and a more robust frontend state manager like Zustand or Redux if the app grew larger.
